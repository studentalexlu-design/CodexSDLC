# 症狀清楚、原因不明

**① 跳過，② 換成下面的 ②′ 與 ②″，④⑤⑥ 不變。** 這條分支的每一步都在防同一件事：還沒有一個會紅的測試就開始猜原因 —— 猜出來的修法會在 ⑤ 被打回，吃掉有限的修正輪。

## ②′ 建迴路

委派 `implementer`（`mode: build`），**唯一交付是一個會紅的測試**，紅在他報的那個症狀上。它照 skill `bug-diagnosis` 做，回來只給測試 path、指令與 exit code。

**②′ 之前不得把原 spec 交給 `implementer`** —— 它會去驗證那份 spec，而不是建迴路。

**②′ 回 `blocked` 說建不出迴路** → 照一般的 `blocked` 問使用者（缺哪筆資料、要哪個環境）。

## ②″ 回查原需求

迴路紅了之後、進 ③ 之前，**你自己查，不問使用者**：從紅測試的 path 出發，`grep -rn 'feature-id:' --include=*.feature` 找出是哪份需求做的，**只讀**那份 `spec.md` 的 Gherkin 區塊、「驗收層」那一行與「交付」各節。

**一次 grep 沒中就停手**，寫進「風險與待確認」直接進 ③ —— **絕不為它多問一輪**。

## ③ 定案

那個紅測試就是驗收條件（**它轉綠 ＝ 完成**）。`spec.md` 的寫法見 skill `spec-authoring` 的「兩個例外」。確認點問的是**「它紅的，是不是你講的那件事」**。

②″ 查到原 spec 的話**同一次順帶問**：原 scenario 的期望值跟他現在報的症狀一不一樣？**一樣 ＝ 當初就是這樣定的，不是 bug** —— 那是需求變更，回 ① 走迭代，④⑤ 整段省掉。

## ④ 修

同一份 `spec.md` 再委派一次 `implementer`。**找到原因後發現有好幾種修法** → 那時才跑一次正常的 ②。
