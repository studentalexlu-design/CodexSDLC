# 除錯：先建迴路，再談原因

**手上有一個可靠地紅／綠的指令，原因就找得到。** 二分、假設檢定、探針全都在消費那個訊號 —— 沒有它，每一步都是猜，而猜出來的修法會在 ⑤ 被打回，吃掉有限的修正輪（預設 3 輪）。

順序不能顛倒：**建迴路 → 最小化 → 假設 → 探針 → 修 → 清乾淨**。

**讀原始碼不是第一步。** 症狀不明時翻程式碼是這條路上最貴的失敗：它沒有終止條件，讀到逾時也不會有結論 —— 那正是「無界的未知不得靠自行擴大掃描補足」講的東西。迴路把無界變成有界。

## ① 建迴路

目標：**一行指令，紅在使用者報的那個症狀上。** 依序試，用第一個做得到的：

1. **一個失敗的測試** —— 最好，因為它到 ⑤ 就直接變成回歸測試
2. **一支 curl／CLI 呼叫** —— 有明確的輸入與可比對的輸出
3. **既有測試 ＋ 特定資料** —— 症狀跟資料綁在一起時
4. **最小 harness** —— 上面都做不到才自己寫一支

**紅的原因必須是那個症狀本身，不是「測試寫錯了」。** 驗法：把你懷疑的那段程式暫時改成明顯正確的版本 —— 迴路要跟著變綠。不會變綠，代表它測的是別的東西，回頭重建。

建不出來 → 回 `blocked`，寫明**試過哪幾種、各卡在哪**（缺測試資料、要 live 環境、症狀本身不穩）。症狀不穩定 → 那不是這個 skill 的問題，先看 skill `test-reliability`。

## ② 最小化

迴路紅了之後，**一次拿掉一樣東西，紅還在就留著拿掉的那個版本**。剩下的全都是承重的。

- 跑得越快越好 —— 後面每一個假設都要跑它一次
- 越小越好 —— 剩下的每一行都是嫌疑人
- **拿掉之後變綠的那一樣，就是線索本身**，記下來

## ③ 假設：一次列 3–5 個，可證偽，先排序

在動任何一行程式之前，**先寫下 3–5 個假設**，每個都要能被迴路判對錯：

```
H1（最可能）：{某條件}下 {某函式} 回傳 {錯的值}
              → 若成立，把輸入改成 {X} 應該會變綠
H2         ：...
```

- **「可能是編碼問題」不是假設** —— 它不預測任何可觀察的結果。假設一定要帶「若成立，會看到什麼」。
- **排序照可能性，不照好查的程度。** 先查好查的那個，最常見的結果是花完時間、排除了一個本來就不太可能的東西。
- 五個都被推翻 → **回頭做 ②**，不是再想五個。多半是迴路還不夠小。

## ④ 探針：一次動一個變數

每個探針都要對應到**一個**假設。同時動兩個變數，兩邊的結果都不能用。

- **有 debugger 就用 debugger**，它不改動程式。
- 一定要印東西 → **全部加同一個前綴**（例如 `[dbg]`），⑥ 才刪得乾淨。
- **探針不寫進提交的程式碼裡** —— 它是一次性的工具，跟修法無關。

跑滿 5 個探針還沒定論 → **回 `partial`**，帶上迴路的 path、已經推翻的假設、下一個最該試的。**別人重來時最貴的就是重建迴路，而那已經在你手上了。**

## ⑤ 修：先寫回歸測試，再改程式

1. **回歸測試寫在對的 seam** —— 跟 `spec.md` 的「驗收層」同一層。寫在太內圈，重構一次就失去意義；寫在太外圈，它抓不到這個 bug。
2. **先確認它紅**，而且紅的理由跟 ① 的迴路一樣。
3. **改最小的一處讓它綠。** 順手改掉「看起來也怪怪的」那幾行，會讓 ⑤ 分不出哪一改才是修好它的。
4. 跑完整的相關測試 —— `failed == 0` 且 `skipped == 0`。

**修法要對得上被證實的那個假設。** 對不上（測試綠了但你講不出為什麼）→ 寫進「風險與待確認」，那通常表示你蓋掉了症狀而不是原因。

## ⑥ 清乾淨

回傳之前，四件事都要做完：

- ① 的迴路重跑一次 → **綠**
- 新的回歸測試 → **綠**，而且把修法還原會讓它紅
- 所有探針、`[dbg]` 輸出、暫時的設定改動 → **全部移除**（`git diff` 掃一次前綴）
- 「做完了」寫**哪個假設成立**，一句話。下一個人靠它判斷這個修法能不能沿用

## 回傳

用共用核心的回傳合約。「證據」欄只給：迴路的指令 ＋ exit code、回歸測試的 path、`total／passed／failed／skipped`。**探針的輸出與完整測試 log 留在檔案裡，回傳只給 path。**

「風險與待確認」要寫的：測試綠了但講不出為什麼、修法蓋住的可能只是症狀、同一個原因可能還影響到別的地方（**具體講是哪裡**，不要寫「可能有其他影響」）。
