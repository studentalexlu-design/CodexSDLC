# 程式碼規範

> **範例檔。** 整份請換成你們團隊自己的。
>
> **格式與命名交給 formatter 與 linter，不要寫在這裡。** 寫進來的代價是每次 `implementer` 委派都付一次 token，
> 而且 `reviewer` 會拿它去佔用只有 3 輪的修正額度。這份只留「工具查不到、但交出去會出事」的東西。
>
> 讀這份的是 `implementer` 與 `reviewer`。上限 150 行。

## MUST

- **對外邊界一定要驗輸入。** API handler、訊息消費者、檔案匯入 —— 不得假設上游給的是乾淨的。
- **例外不得吞掉。** `catch` 之後要嘛處理、要嘛往上拋並保留原始例外。空的 `catch` 是必修。
- **不得在程式碼裡寫死密碼、連線字串、API key、正式環境位址。** 一律走設定或 secret store。
- **對外回傳的錯誤訊息不得帶內部細節** —— 不含 stack trace、SQL、內部主機名或路徑。
- **公開介面的破壞性變更**（刪 public 方法、改簽章、改語意）必須在 `spec.md` 明寫。
  共用 library、CLI 參數、事件 schema 都算。
- **不得為了讓測試過而改測試。** 測試本身有問題 → 寫進回傳說明，讓 orchestrator 決定。

## SHOULD

- 新程式碼不加沒有人要求的擴充點：策略介面、設定開關、「以後可能會用到」的抽象一律不做。
  （**輸入驗證、錯誤處理、安全性、測試不算多做** —— 「最小」不能拿來砍掉這四項。）
- 一個函式做一件事；巢狀超過 3 層就先抽出來。
- 非同步一路到底，不得在同步方法裡 block 等待非同步結果。
- 記錄日誌時帶得上關聯 id；**不得把個資或憑證寫進日誌**。
- 註解寫「為什麼」，不寫「做了什麼」——「做了什麼」讀程式碼就知道，而它會過期。

## 這裡不管的事

- **縮排、括號、命名大小寫、import 順序** —— formatter／linter 的事。寫進來只會讓審核在風格上空轉。
- **目錄怎麼擺、分幾層** —— 現況，`sa-analyst` 查完寫進 `bdd-docs/project-map.md`。
