# 前端規範

> **範例檔。** 請換成你們團隊自己的規範；不指定框架。
>
> 涉及前端時由 `sa-analyst`、`implementer` 與 `reviewer` 讀取，搭配適用的 coding.md 與 testing.md。上限 150 行。

## MUST

- **元件責任與資料流要明確。** 共用資料需有明確擁有者；不得直接修改由外部傳入且不屬於元件的狀態。
- **API 串接須處理需求涉及的載入、成功、空資料及失敗狀態。** 失敗不得顯示成成功；重送、重試與過期回應不得造成錯誤畫面或重複操作。
- **表單必須提供可理解的驗證結果。** 錯誤要能對應欄位，送出期間的互動與失敗後保留輸入的行為依 spec.md；前端驗證不能取代伺服器驗證。
- **互動控制項須能以鍵盤操作，具有可辨識名稱與可見焦點。** 表單欄位須有標籤；錯誤與狀態不得只靠顏色表達；對話框等互動須合理管理焦點。
- **在 spec.md 約定的檢視尺寸下，主要內容與操作必須可用。** 不得因內容截斷、遮擋或版面溢出而無法完成流程。
- **不可信內容不得直接當 HTML 或可執行程式插入。** 必要的富文字使用專案核准的清理機制；前端程式、儲存與日誌不得放入秘密，畫面隱藏不能充當授權檢查。
- **驗收測試須經過指定的 UI 介面。** 不得只呼叫內部方法，或 mock 掉受測元件、事件處理與狀態轉換；外部 API 可在邊界替身化。
- **API 替身須對齊來源。** request、response 與錯誤的欄位、型別及格式依既有 schema、API 文件或樣本，記錄來源路徑；不強迫新增 OpenAPI。缺少來源或只能假設的部分須列為待確認，不能把猜測當成契約。
- **交付須區分替身驗證 UI 與真實 API 契約驗證。** 只用替身測過時明說來源與限制；只有實際完成真實 API 契約驗證，才可回報其已驗證，並附驗證範圍與證據。存取外部環境仍依既有批准規則。
- **專案採用視覺回歸時，baseline 須有依據。** 建立或更新前對照已確認設計與預期差異，保留設計來源及更新理由，不得只為消除失敗而重錄。預期畫面或差異超出已確認設計、尚無法決定時，回到既有需求缺口與定案確認流程；不另設固定人工批准關卡。

## SHOULD

- 沿用既有元件、設計系統、狀態管理與 API client；不要為本次需求引入第二套。
- 元件只承擔自己的呈現與互動責任；跨元件規則、資料轉換與網路存取沿用專案分工。
- 使用語意化 HTML 與原生控制項；新增自訂互動前先確認原生能力不能滿足需求。
- 響應式版面以內容需求決定斷點，測試約定尺寸與長文字等邊界；不要自行發明產品支援的裝置範圍。
- 依風險選擇元件測試或瀏覽器測試；視覺 snapshot 不能單獨證明互動、無障礙或流程正確。
