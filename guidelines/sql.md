# SQL 與資料存取規範

> **範例檔。** 整份請換成你們團隊自己的。
>
> **能寫成 regex 的一律搬到 `rules.json`** —— 那邊零 token 而且擋得住，這邊是榮譽制而且每次委派都要付錢。
> 這份只留「判斷題」：什麼時候可以寫原生 SQL、邏輯該放哪一層。
>
> 讀這份的是 `sa-analyst` 與 `implementer`。上限 150 行。

## MUST

- **業務規則不進資料庫。** 新的判斷邏輯不得寫進 View／Stored Procedure／Trigger —— 它們測不動、
  改動看不見、版控管不到。舊系統既有的不在此限（那是逆推的對象，不是模仿的對象）。
- **不得用字串串接組出 SQL。** 一律參數化。動態條件用 query builder 或 ORM 的組合 API。
  （這條 `rules.json` 也擋，但擋不到所有寫法 —— 看到就當必修。）
- **每一次結構變更都要有 migration 檔**，且**可回滾**。不得手動改正式環境的 schema。
- **不得在 migration 裡寫資料修補（backfill）與結構變更在同一個交易**。分開，各自可回滾。
- **刪欄位／改型別／改欄位語意 = 破壞性變更**，必須在 `spec.md` 明寫並取得使用者批准才動。
- **不得下 `SELECT *` 進到應用程式的型別**。欄位一加，反序列化就靜默地多一份東西。

## SHOULD

- 讀取用 ORM，效能真的不夠才降到原生 SQL —— 而且要在程式碼註解寫出「為什麼 ORM 不夠」。
- 一次查詢一個聚合根。跨聚合的組裝在應用層做，不要在 SQL 裡 join 五張表。
- 交易範圍越小越好；不得在交易裡呼叫外部服務。
- 新表一律有 `created_at`、`updated_at`（UTC）。
- 索引跟著查詢走：新增查詢條件時一併評估索引，把結論寫進 `spec.md` 的風險欄。

## 大表的線上變更

正式環境**列數超過 100 萬**的表，加索引／改欄位一律線上進行（`ONLINE = ON` 或等價作法），
並在 `spec.md` 的「影響」寫明預估鎖表時間。**這一條命中的話，那次交付必須停下來等使用者批准** ——
它動到的是正在跑的流量。

## 這裡不管的事

- **現在用哪套 ORM、repository 放哪** —— 現況，`sa-analyst` 查完寫進 `bdd-docs/project-map.md`。
- **舊系統的 SP 寫得對不對** —— 那是逆推的素材。判斷「哪些是業務規則、哪些只是資料存取」是 `sa-analyst` 的工作，不是規範能決定的。
