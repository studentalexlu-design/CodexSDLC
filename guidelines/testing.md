# 測試規範

> **範例檔。** 整份請換成你們團隊自己的。
>
> 讀這份的是 `implementer`（寫測試前）與 `reviewer`。上限 150 行。

## MUST

- **測試要先看它紅。** 沒紅過的測試不算測試 —— 它可能永遠是綠的。
- **`skipped` 不是綠燈。** 交付時 `failed == 0` 且 `skipped == 0`；真的要 skip 就寫進「風險與待確認」。
- **不得 mock 掉被測的邏輯本身。** 判準：**把實作整段刪掉，這個測試會不會還是綠的？** 會的話它沒在測東西。
- **斷言要斷到值。** 只斷言「沒有丟例外」或只斷言非 null 的，視同沒有斷言。
- **測試不得依賴執行順序，也不得共用可變的 static 狀態。** 平行執行會炸，而症狀是隨機失敗。
- **`.feature` 的步驟文字必須與 `spec.md` 的 Gherkin 區塊逐字一致。** 那是使用者批准的字，也是 QA 拿到的字。
- **改到既有 step 的措辭一定要回報**（哪些 step、舊措辭、新措辭）。QA 的自動化綁在那些文字上，
  改掉會讓他們的測試**靜默斷掉，而且斷在他們的 repo**。加新 step、加 scenario 不算。

## SHOULD

- 從外往內：先讓驗收層表達「使用者看到什麼」，再往內補單元測試。內圈的測試是為了驅動設計，不是為了覆蓋率數字。
- 一個測試一個行為；測試名字寫出「什麼情況 → 期望什麼」。
- 邊界值要有測試：空集合、剛好命中門檻、剛好超過門檻、null。
- 外部相依（HTTP、時間、亂數、檔案系統）從邊界注入，不要在測試裡改全域狀態。
- step definition 為重用而寫：業務邏輯不堆在 step 裡，共用狀態走建構子注入或 scenario context。

## 測試框架

- C#：**Reqnroll**（不是 SpecFlow）｜Java：**Cucumber**
- 專案已經在用別的就沿用，**不要引入第二套**。
- `.feature` 與 step definitions 跟該專案的單元測試放在一起（**不在 `bdd-docs/` 底下** ——
  那是流程草稿區，QA 不會去那裡找測試）。已經有 `.feature` 的話沿用既有目錄與命名慣例。

## 這裡不管的事

- **覆蓋率數字門檻。** 覆蓋率不是 oracle：能刪掉實作還全綠的測試照樣有 100% 覆蓋率。
  要看的是上面 MUST 的第三條。
